How the Trade Mark Ontology is built, and what it takes to run

The ontology is a set of plain text files that describe the Manual, the Act and the Regulations as a network of ideas, each tied to the passage it came from. This guide walks through how those files are structured, which public standards they follow, and the work an office would take on to adopt and maintain them.

1 · Overview

The whole system on one line

Nobody types the knowledge graph directly. People and models write records: short, structured entries such as "this concept, with these labels, drawn from these passages". A program then builds the graph from the records, checks it against a set of rules, and publishes it. If the graph is wrong, you fix the record and rebuild. This one habit is what keeps the system auditable.

2 · Standards

The standards it uses, in plain terms

Almost everything is built on open standards from the World Wide Web Consortium (W3C), the body that also maintains HTML. That matters for adoption: the files are not tied to one vendor, any compliant tool can read them, and staff with "semantic web" or "linked data" skills will recognise them.

The core idea is simple. Every fact is a three-part sentence: a subject, a relationship, and an object. This is called a triple.

Subjectgeographical reference
Predicate (relationship)may give rise to
Objectconnotation

A knowledge graph is just a large collection of these sentences. Because the objects of some sentences are the subjects of others, they join up into a network you can walk through.

RDF

W3C · 2004, 2014

The rule that every fact is a triple. Every other standard here is built on it.

Like a register where every entry has exactly three columns.

all files in graph/

IRI

IETF · 2005

A permanent web-style address that names one thing, so two systems agree they mean the same section or passage. Ours are built from the Manual's and Act's own reference numbers.

Like a trade mark number: one identifier, never reused.

src/tm_knowledge/refs.py · docs/IDENTIFIERS.md

Turtle and N-Quads

W3C · 2014

Two text formats for writing triples down. Turtle (.ttl) is readable by people. N-Quads (.nq) puts all four graphs in one file for software.

Like the same register printed as a report, or exported as a spreadsheet.

graph/*.ttl · graph/dataset.nq

RDFS and OWL 2 RL

W3C · 2004, 2012

The schema: what kinds of thing exist ("a ground of refusal is a kind of legal concept"), which can never overlap ("a Manual passage is never a legislative provision"), and simple rules a computer can apply. RL is a deliberately limited profile that runs fast and predictably.

Like the Manual's own definitions section, written for a machine.

ontology/draft/ (9 modules)

SKOS

W3C · 2009

The standard for thesauri and controlled vocabularies: one preferred label, any number of alternative labels, and "broader" for "is a kind of". We add one field SKOS lacks: not-label, a term that must never be read as this concept.

Like a thesaurus with "see also" and "do not confuse with".

every concept node

PROV-O

W3C · 2013

A vocabulary for provenance: who or what produced a statement, when, and from what. The project's own fields (review status, model, evidence span) extend it.

Like the history panel on a file in a case management system.

ontology/draft/provenance.ttl

SHACL

W3C · 2017

"Shapes": rules the data must satisfy, each with a plain-language message. A violation blocks publication; a warning is reported for a person to look at.

Like a formalities check that runs on every filing, every time.

shapes/ (5 files, 25 shapes)

SPARQL

W3C · 2008, 2013

The query language for graphs. A query is a pattern of triples with blanks; the answer is every way the graph can fill them in. CONSTRUCT queries also write new statements, which is how rules are expressed.

Like a search of the register by any combination of fields.

queries/competency/ · queries/rules/

Named graphs

part of RDF 1.1

A label on a set of triples saying which collection it belongs to. We use four: source text, expert-signed, machine-written, and machine-inferred. A query has to ask for a collection by name to see it.

Like separate physical files for approved and pending matters.

graph/README.md

Around the standards sits ordinary engineering: YAML for the records people edit, Python with the open-source libraries rdflib (reads and writes RDF) and pySHACL (runs the shapes), pytest for tests, Git for history and GitHub Actions to run every check on every change. Nothing is licensed software.

3 · Layer 1

The source text: passages, provisions and citations

The bottom layer restates the Manual and the legislation without interpreting them. It comes from a separate extraction tool that splits each Manual page into chunks (passages) and each provision into units, and gives every piece a stable reference. Those references are the keys that everything else hangs off.

SourceReference formExampleMark used on screen
Manual passageTMM/Part‹n›/…TMM/Part31/1#1square
Act provisionTMA1995/s‹n›…TMA1995/s39(1)diamond
RegulationTMR1995/r‹n›…TMR1995/r3A.3hexagon

Each reference becomes an address by adding a fixed prefix. TMM/Part31/1#1 becomes https://data.ipaustralia.gov.au/tmk/ref/TMM/Part31/1%231. The # is the only character that has to be rewritten (as %23), because on the web it means "a part of this page". One passage reference in five contains one.

    tmk:mention         "Subsection 39(1)" ;
    tmk:extraction      "href" .   # the Manual's own hyperlink

Why a citation is a separate object, not a plain link

The extraction tool records how it found each reference. href means the Manual's authors hyperlinked it. regex means software read it out of the prose, and then certainty says how sure: explicit, default (a bare "section 43" assumed to mean the Act), or ambiguous (several instruments could be meant, and the tool refused to guess). A plain link would lose that, so each of the 2,236 citations in the graph is stored as its own small record. The system never resolves an ambiguous one by guessing; it puts the passage in front of a person.

The Manual is practice, not law, and the model enforces it. A Manual passage and a legislative provision are declared disjoint classes: nothing can be both. Every passage also carries the text label practice, law or decision, which survives even when data is copied out of the graph. This matters because the Manual quotes the Act in places, so a passage can look like law while being practice.

4 · Layer 2

Concepts: the vocabulary of examination

A concept is one idea from trade marks practice: connotation, prescribed sign, priority date, the Registrar. Each is a SKOS concept with labels, links to the passages it is drawn from, and the provisions it operates under. Concepts are what connect a question in an examiner's words to the right passages.

Field names became standard terms (pref_label became skos:prefLabel), references became addresses, and the provenance became a stamp on the node itself. Labels carry a language tag, @en-AU, because the system compares names in Australian English.

The not-label, the field SKOS does not have

"Deceptively similar" is a not-label of the signed concept likely to deceive or cause confusion. Both are about confusion, but one belongs to section 43 and the other to section 44. A search tool that treated them as synonyms would send an examiner to the wrong test, and the mistake would be invisible. Two checks follow from this: a term cannot be both a label and a not-label of the same concept (a defect), and a term that is one concept's not-label and another's preferred label is reported so a person can see the boundary (expected, not a defect).

Eleven kinds of concept, in three families

Each concept is given one kind by a separate typing record, so the decision "is this a test or a principle?" carries its own evidence and author. The kinds are grouped into three families, and the families are classes in the schema too.

The law's questions

tmk:LegalQuestion
  • Ground of refusala statutory basis to reject
  • Legal testa question the decision maker must answer
  • Principleonus, standard, presumption of registrability

What they are asked about

tmk:ExaminedMatter
  • Subject matterthe mark and its kinds: shape, certification mark
  • Sign contentwhat it contains or conveys: a geographical reference
  • Contextthe goods, the market, a reputation, a date
  • Use in tradeusing, authorising use, prior use

The process

tmk:ProcessElement
  • Process rolethe Registrar, a delegate, the applicant
  • Procedural stepexamination, acceptance, lapsing
  • Instrument or recordthe Register, an endorsement, a notice
  • External instrumentthe Madrid Protocol, the WHO's INN list

What a concept is is its kind. What it does is a relationship. "Relevant factor", "exception" and "remedy" are not kinds you file a concept under. The schema defines them by their links: anything that qualifies a test is a relevant factor; anything that does not by itself give rise to a ground is an exception; anything a ground is overcome by is a remedy. The computer works the class out from the link (OWL "equivalent class" restrictions), so a concept is a factor only because something says what it is a factor for.

5 · Layer 3

Relationships: a closed dictionary of 52 verbs

Relationships are the predicates in the triples, the verbs that join concepts, provisions, passages and decisions. The list is closed: a record may only use a relationship that is in the dictionary. With an open list, a wrong relationship and a new one would look the same, and accuracy could not be measured.

Every entry in the dictionary carries six things: a definition, how it reads aloud (subject first), an example from a real record, a counter-example saying what it is not for, whether its authority is law or practice, and which kinds it may join. A machine-written relationship whose ends are the wrong kinds is refused.

Every relationship is stored twice

A relationship goes into the graph as a plain triple, which is fast to search, and as an assertion record about that triple, which holds the evidence and who wrote it. Technically this is called reification. Either alone fails: the plain triple is anonymous, and the assertion alone is slow to query. A rule check fails the graph if a plain triple appears in the signed collection with no signed assertion behind it.

6 · Provenance

Who wrote it: three states that never blur

Since September 2026 a model has been allowed to write legal content (definitions, types, relationships), provided nothing it writes can be mistaken for something an expert signed. This is the rule the whole structure is built around, and it is enforced in four independent places: the folder, the named graph, a stamp on every node, and the rule checks.

Authored

Written by a model or an agent. No person has looked at it. May be shown to examiners, always labelled "Machine · unreviewed".

authored/ → graph/authored.ttl
Approved

A named expert read and signed it on a date. The 190 records signed so far are frozen as the yardstick for measuring everything else.

eval/gold/ → graph/approved.ttl
Rejected

A named expert threw it out. Its identifier is retired with the reason and never reused.

retired-ids.yaml

A record moves from authored to approved only through a recorded human decision: a reviewer marks up a workbook, and one program (tmk-transcribe) reads the signed workbook. Age, silence and an agent's opinion never promote a record. The field approved_by on a machine-written record is a violation that blocks publication.

7 · Quality

The quality gates

Every change to the repository runs the same sequence of checks automatically. A failure stops the change from being published. The shapes are not loosened to make a build pass; the data is fixed, or the reason the rule was wrong is written down as a decision.

CheckWhat it catchesTool
Record validationA record missing its envelope, a quote that does not match its span, an unknown relationship. Malformed records are refused and named, never skipped.authored.store

Here is one shape, with its translation. Each shape has a test file that deliberately breaks it, to prove it fires, and where possible a near-miss that must not fire.

# shapes/provenance.ttl (abridged)
tmk:AuthoredAssertionShape a sh:NodeShape ;
    sh:targetClass tmk:AuthoredAssertion ;        # check every machine-written relationship
    sh:property [
        sh:path tmk:approvedBy ;
        sh:maxCount 0 ;                           # it may have no approver at all
        sh:message "A name in approvedBy on an authored assertion. It means a person
                    read this and signed it, and no agent writes it." ;
    ] .

Severities. A violation is a defect: publication stops. A warning is a gap for a person to look at. A note is information, such as the list of concept pairs where one's not-label is another's name.

8 · Use

Asking the graph questions

The ontology was designed backwards from competency questions: questions it must be able to answer, written before the model. Thirteen are written as SPARQL queries today. Each file states the question, then its limits in plain words, then the query.

# question: CQ-0017
# answers: If section 43 were amended, which parts of the Manual would need reviewing?
# limits: Reviewing effort, not reviewing outcome. A Part appears because a passage
#   in it cites the provision, not because an amendment would change its meaning. …

SELECT ?part (COUNT(DISTINCT ?chunk) AS ?passages)
       (SUM(IF(?extraction = "href", 1, 0)) AS ?authored)    # linked by the Manual's authors
       (SUM(IF(?certainty  = "default", 1, 0)) AS ?inferred) # read out of prose
WHERE {
  GRAPH tmkg:source {
    ?citation a tmk:Citation ;
              tmk:citingPassage  ?chunk ;
              tmk:citedAuthority tmkr:TMA1995/s43 ;
              tmk:extraction     ?extraction .
    ?chunk tmk:partId ?part .
  }
}
GROUP BY ?part

In plain words: find every citation in the source collection that points at section 43, take the passage it sits in, and count passages per Manual Part, splitting those the authors linked from those software inferred. This is the query an amendment would start from.

Rules are queries that write new facts. RULE-0001 flags a Manual passage that mixes quoted legislation with the Registrar's practice, so anything built from it must keep the two apart. Both rules are marked PENDING: until an owner approves them, everything they produce is stamped as a candidate.

The examiner explorer and "Ask the Manual" do not query the graph live. When the site is published, a build step exports the concepts, relationships and passages to JSON files, and the browser searches those. The search code exists twice, in Python for measurement and in JavaScript for the page, and a test holds the two identical.

9 · Adoption

What adoption involves

Taking the ontology into a Manual uplift project means owning four things: some decisions only the office can make, a small amount of infrastructure, a set of roles, and a review effort. None of it needs new licensed software.

Decisions the office has to make before go-live

  • Confirm the permanent web address

    Every identifier is built on https://data.ipaustralia.gov.au/tmk/, which is proposed and not confirmed. Permanent addresses need control of the domain. Changing it later is a configuration change and a rebuild, but anything outside that has stored the old addresses breaks.

    Office, with web and records management
  • Decide who signs

    The plan is a panel of examiners who review the whole ontology at once. Name the panel, the sign-off form (today a workbook) and what a signature means.

    Content owner
  • Approve or replace the draft schema

    The nine modules in ontology/draft/ are a proposal. Each is promoted to ontology/ on a recorded decision by an ontology specialist and a domain expert, one module at a time.

    Content owner and ontology steward
  • Rule on the open modelling questions

    The two pending rules; whether any relationship should be restricted to particular kinds of subject (each carries counts of what it has actually joined, as evidence); four disputed signed readings.

    Content owner
  • Decide whether models keep writing

    If yes: which model, a spending cap, and the rule already in force that an expert's own review notes never go into a prompt.

    Content owner, with budget holder

Infrastructure modest

  • A Git repository with automated checks

    GitHub with GitHub Actions today; any agency Git and CI service will do. Every change runs the tests, the graph drift check and the rule checks.

    Data engineer
  • The upstream extraction tool

    manual-XtrACTor produces the snapshot. Someone has to run it when the Manual or the Act changes and pin the new version.

    Data engineer
  • Python 3 with open-source libraries

    rdflib, pySHACL and pytest. A full test run takes about ten minutes.

    Data engineer
  • Static web hosting for the explorer

    Plus, if live answers stay on, a small service that holds the model key so it is never in the page.

    Data engineer
  • Later, optionally: a triple store and a search engine

    The roadmap names Apache Jena Fuseki (to query the graph live) and OpenSearch (keyword plus meaning-based search). Neither is needed for the current files and both are deliberately not built yet.

    Architecture decision

10 · Maintenance

What maintenance involves

Most maintenance is triggered by a change in the source text or a decision about meaning. The system does the detection; people do the judgement.

Why the content hash is the heart of maintenance. Every piece of evidence stores a fingerprint of the exact passage text it quoted. When the Manual changes, the system does not need to understand what changed; it only needs to see that the fingerprint no longer matches. That turns "re-check the whole ontology after every Manual release" into "re-check these specific records".

11 · Limits

Limits to know before you commit

  • Nothing in the schema is approved. All nine modules are drafts, and 112 concepts and 352 relationships are machine-written and unreviewed.
  • It never states an examination outcome. It finds the right concepts and passages and cites them. Deciding whether a ground applies stays with the examiner, by design.
  • No "as at a date" questions. The snapshot has no version history, so "what was the practice on 1 March 2024?" cannot be answered. That needs a different data strategy.
  • Complex legal rules are out of scope. Rules with exceptions to exceptions (the LegalRuleML standard) were deliberately deferred.
  • Coverage follows the records. The source graph holds 1,056 of the 2,460 Manual passages: those something has been written about, and their neighbours. Passages nobody has spoken about are in the snapshot but not yet in the graph.
  • The permanent address is unconfirmed, and the relationship dictionary's definitions are themselves machine-written and unreviewed.
12 · Reference

Glossary

Assertion
A record about a fact: who stated it, from which passage, and its review status.
Chunk
One passage of a Manual page, the smallest unit the system cites.
Class
A kind of thing in the schema, such as Ground of refusal or Manual passage.
Closed list
A fixed set of allowed values. Records may only use relationships on it.
Competency question
A question the ontology must be able to answer; the test of whether it is fit for purpose.
Content hash
A fingerprint of a passage's exact text. Any edit changes it.
CI
Continuous integration: checks that run automatically on every change.
Disjoint
Two classes that can share no member. A Manual passage is never a legislative provision.
Envelope
The provenance block on every machine-written record.
IRI
A permanent web-style address that names one thing.
Named graph
A labelled collection of triples. We have source, approved, authored and inferred.
Not-label
A term that must never be read as a given concept.
Ontology
The schema: classes, relationships and rules that say what can be stated and how.
Predicate
The middle of a triple: the relationship.
Ref
The extraction tool's stable reference for a passage or provision, such as TMA1995/s43.
Reification
Making a statement about a statement, so a fact can carry its evidence.
Shape
A SHACL rule the data must satisfy before publication.
Snapshot / pin
One fixed version of the extracted Manual and legislation, identified by a commit number.
Stale
A record whose passage text has changed since it was written.
Triple
One fact as subject, predicate, object.
